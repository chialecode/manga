## 1. 交付原则

按 2026-09-25 用户明确要求，整个软件先形成包含全部基本功能的 MVP，再根据使用反馈持续 loop 迭代。以可用的完整工作流作为批次成果，优先拓展基本功能覆盖；视觉打磨、便利功能、无关重构与优化不要求在每个模块继续之前清零。稳定引用、统一命令、真实停用与数据恢复仍是基础质量要求。阶段按真实依赖推进，不承诺未经验证的固定日历工期。

文档完成仅意味着已经形成可评审方案。本文维护 POC 和 AT 的用例定义；实际执行结果统一见 [执行台账](status.md)，不能从本文的计划或预期判断功能已经可用。

A-40：每轮 A 技术规划先查证可用的活跃开源方案，再给集成和验证路径。通用能力优先采用成熟方案，MANGA 投入组合、业务身份、权限、恢复与完整体验；可逆接入依次进行，不为 MVP 全面推倒现有系统。证据和自研例外口径见[选型规则](../dev-rules/architecture-and-contracts.md#open-source-first)。

[组合架构](../design/composable-ai-native-architecture.md)与[外部提供者](../design/external-providers-and-acquisition.md)的验收用例使用可控提供者；首批真实服务是 Bangumi，下载协议是 BitTorrent。

POC-07 使用 MANGA 的统一契约和场景验证运行时候选。自研最小实现和适配实现均可纳入验证，最终选择以契约满足程度、可靠性和维护成本记录为准。

### 2.3 待实现

MVP 范围内没有待实现的基本能力。vNext：Game 场景、更多格式、其他桌面系统、同步与协作等，需要明确的用户需求与独立设计，另行定义验收，不计入当前完成度。

A-39 在 A-33 优先级上明确全软件 MVP 路径：已交付 Agent/基础配置 → 阅读与人工记录基本闭环 → 小说、漫画、动画基本试用 → 录音整理、创作组织、限定粗剪与扩展获取的基础闭环，最后形成贯通的 MVP；早期反馈可随时进入台账，但不能把“等用户反馈”变成推进尚缺基本功能的默认前置。功能实施按依赖可并行衔接，不等待前一模块所有非阻塞余项。MVP 不自动表示全部 AT 的产品验收通过。

<a id="mvp-loop"></a>
### 全软件 MVP 基线与反馈循环

“全部基本功能”按现有需求主线解释，范围如下；不引入 vNext，也不因 MVP 名称取消已确认的格式、权限、来源和恢复承诺。可按阶段交付试用，直到下表基础链路都存在且可验证，才称全软件 MVP；单个阅读切片或动画演示不等于 MVP 完成。

| 基本能力 | MVP 必须能完成的流程 | 可由后续 loop 深化 |
| --- | --- | --- |
| 资源库/配置/恢复 | 配置目录、导入/查询、来源身份、进度与重启、备份及资料包往返；无 AI 仍可用 | 更丰富的管理视图、批量便利操作、非必要统计 |
| 小说/漫画/动画 | 已确认格式目标的基本阅读/播放、常用控制、位置/选区、笔记与来源返回；不能用静态演示冒充播放 | 外观密度、更多偏好与快捷操作、额外格式及超出基础预算的优化 |
| 人工/语音记录与 Agent | 人工编辑/保存/历史；主动录音/转写/整理及采集位置关联；BYOK、材料范围、取消和失败恢复 | 更多整理模板、便利工具与非必要自动化 |
| 创作组织 | 项目材料、白板/导图/文案的基本编辑和互引、来源跳转、项目导出恢复 | 高级布局、模板、协同和自动排版；协同仍属 vNext |
| 粗剪/获取/模块 | 已限定的无转码剪拼/导出，Bangumi/BitTorrent 基础接入及恢复；可信模块可启停，关闭后保留数据 | 高级剪辑、额外提供者、第三方分发生态；开放不可信执行前仍须满足隔离门槛 |

每个 loop 按“A 制定覆盖整个阶段的计划 → B 连续实现/自测 → A 一次集中复核并处理局部修复 → 经用户授权 push/PR/合并 → 规划下一阶段”推进（A-46）。用户的人工检查、反馈与决定走另一条流水线：记在[用户待办](../../USER-ACTIONS.md)，在任何阶段逐项处理，不阻塞上述循环（A-53）；反馈带来的修复进入当时正在进行的阶段。阶段计划列出该阶段的全部交付与退出条件，不拆成多批交回。先补尚缺的基本链路，再按影响处理反馈和延期项；不以内部测试轮次或两个边缘示例为交接单位。

非阻塞项统一登记在[执行状态的后续 loop](status.md#followup-loops)，写明实际影响、替代路径、负责人、承接循环/触发条件和复测入口。不能延期当前基本流程不可用、数据/来源损坏、授权突破、无法恢复或已触发的必需性能门禁；可隔离问题只限制受影响功能，不冻结全软件独立开发。没有后续循环承接的当前必须项应在当前范围关闭，不能无限期以“之后优化”结案。

H/AT 人工与产品验收状态按版本分别记录；缺真实设备可以保留 not-run 并继续无依赖实现。阶段合并只要求 Agent 侧完成（必需用例与自动证据通过、A 审查收敛、无阻塞项）与用户授权；人工检查可顺延到后续阶段，按实际执行的版本记录。MVP 试用、正式验收、阶段合并与对外发布是不同事实，外部操作继续按会话授权。

## 3. 验证任务（POC）

| 编号 | 验证问题 | 方法与必须留下的证据 |
| --- | --- | --- |
| POC-01 | 阅读引擎适配、解析与稳定定位是否可靠？ | 优先验证活跃开源引擎；用 TXT/EPUB/MOBI/PDF、中文/日文/emoji 样本建立锚点，改变字号、窗口和解析规则，记录恢复结果；比较源结构、规范文本与 DOM 映射 |
| POC-02 | 用户语音能否正确采集并关联内容时间？ | 分别测试耳机和外放；记录设备、回声处理、录音采样偏移、延迟、暂停/倍速/跳转；报告误收录情况与定位误差 |
| POC-03 | 目标动漫样本和无转码导出可否实现？ | 建立 MP4/MKV、H.264/HEVC、AAC/ASS、多音轨和 VFR 矩阵，比较候选后端；验证关键帧切点、时间基、音画同步与不兼容拒绝；给出发布支持清单 |
| POC-04 | 能力协议是否支持停用与独立宿主？ | 用最小模块完成依赖解析、工具调用、事件、启停和晚到回调测试；在另一宿主装配小说核心能力 |
| POC-05 | 编辑和互嵌的基础行为是否可靠？ | 测试中文输入法、选区、撤销、块 ID、源编辑与布局编辑区分、循环嵌入占位；决定必要编辑/绘制基础技术 |
| POC-06 | 本地数据、搜索和恢复是否满足目标？ | 用基准库测试 SQLite 单写入、事务事件、全文中日文检索、备份往返、升级失败回滚和响应时间 |
| POC-07 | 组合运行时候选是否满足 MANGA 的契约、可靠性与维护目标？ | 同一 SDK、能力图、故障夹具和三个小型业务场景比较；验证多 Facet、single/many、依赖变化、显式关闭、重复释放、失败清理和恢复；记录版本、维护成本及限制，只选一个生产实现 |
| POC-08 | 多动漫数据库组合能否保留身份与用户意图？ | 两个固定假提供者产生冲突、同名跨媒介作品、超时与空字段；验证候选匹配、用户锁定、换源、断网和资料包往返 |
| POC-09 | 后装下载能否可靠连接本地导入？ | 用受控 HTTP 服务测试取消、ETag 变化、同名冲突、跨卷与磁盘不足；在文件发布/入库边界注入进程中断，证明恢复可核查且不重复入库 |

POC-04 增加模块停用提交屏障与旧 epoch 回调样本；POC-07 是组合机制的进入条件。POC-08/09 的早期原型只验证契约，已由 Bangumi 的产品实现与 BitTorrent 获取的产品实现分别再次验收；HTTP/ETag 证据不证明 BT 分片和断点恢复。

POC 结果使用[验证报告模板](../templates/validation-report.md)，保存到 `docs/evidence/` 并链接到[执行台账](status.md)，包含可公开的平台/构建信息、样本指纹、依赖版本、步骤、实际结果、限制与设计决定。失败结果应回到模型或边界调整，不以绕过验收的特殊分支掩盖问题。

### 3.1 POC-07 运行时验证与选择

候选原型消费同一插件 SDK、静态清单和装配意图，运行同一组业务夹具；运行时差异留在宿主边界，不修改业务插件去迎合不同候选。原型分别运行，不要求同时装入一个生产宿主。

自研最小实现与适配实现都必须说明服务注册、作用域、清理、热变更和故障恢复的实际行为。先验证必要契约，再决定是否需要补充候选，不预设固定数量的完整实现。

| 验证项 | 共同验证输入 | 必须留下的证据 |
| --- | --- | --- |
| 依赖与配置 | required/optional、single/many、缺失/循环依赖、用户明确关闭、Bundle 冲突 | 确定性绑定、可解释影响链、无隐式重新启用；对应 AT-36 |
| 生命周期 | 中途激活失败、重复/重入释放、停止期间注册资源、晚到回调与提交竞态 | 启停时间线、残留资源计数、旧 epoch 拒绝；对应 AT-14、AT-37 |
| 结构变化与恢复 | 增删依赖、换提供者、候选失败、进程中断和配置重启 | 明确热变更/重建/重启范围；上次有效配置与业务数据可恢复；对应 AT-17、AT-48 |
| 多运行环境 | 服务与 UI Facet、解析 worker、IPC 取消、丢序后重新取快照 | 序列化协议、调用来源、断连恢复；原型验证最小链路，产品接入另行验收 |
| 三个组合场景 | 阅读器移除后恢复资料；双假数据库换源；下载组合加入后导入再移除 | 相同业务输出与数据身份；复用 POC-08/09 夹具，对应 AT-38、AT-41、AT-42/43 的原型子集 |
| 维护与成本 | 相同契约变化、依赖版本升级和故障诊断任务 | 实现/适配与测试投入、必要兼容层、代码依赖方向、平台限制、启动和启停资源测量 |

选择顺序如下：

1. 先检查必需契约和数据不变量。激活失败泄漏、停用后继续写入、身份变化或无法恢复，均不能以实现更快或代码更少抵消。
2. 通过必要行为后，比较维护范围、诊断能力、依赖演进成本和实测性能。分别记录运行时语义、契约补齐、兼容性和依赖升级的维护责任。
3. 记录选择理由、未选择候选的具体不足、热变更范围及仍需完成的能力。只有满足必要契约且维护范围可控的候选可以进入生产实现。
4. 若所有候选都不满足，缩小或修正契约与原型后继续验证；不能默认为任一候选通过。结果选定后，发行版仅保留一个运行时实现，未选原型不进入生产依赖。

功能停用与重新启用属于必需行为。包代码升级、原生组件替换与复杂依赖图变化允许先要求重启，但必须准确展示实际生效状态。原型的可信插件验证不证明第三方隔离已完成；AT-34/45/47 按实际执行边界验收。原型结果与完整产品验收分别记录，不能用场景子集通过替代 AT 用例完成。

## 7. 质量检查的执行层次

1. **领域与契约检查**：锚点映射、引用闭包、进度区间、命令校验、幂等、修订冲突与模块生命周期。
2. **样本集成检查**：解析器、音频时钟、媒体后端、文件定位、数据库迁移与索引。
3. **端到端流程检查**：真实界面中的阅读→记录→引用→Agent，以及创作与导出。
4. **人工体验检查**：中文输入、阅读舒适度、对白误收录、文案依据、可访问性与错误恢复。
5. **打包与系统检查**：在目标系统的安装产物中复现关键流程。

测试应覆盖真实约束和失败边界，不以大量重复实现逻辑的测试替代样本与完整流程。通过后只有实现变化或新风险出现才扩大重复范围。

## 8. 发布门槛

- 当前阶段所有“必须”需求都有执行记录和可复现结果。
- ID、引用、已确认保存的记录和用户内容不存在已知的数据损坏问题。
- UI 与 Agent 命令没有绕过权限或业务校验的路径。
- 格式清单、模型能力和插件信任边界与实际实现一致。
- 备份与恢复至少完成一次往返验证；涉及格式升级时验证迁移失败恢复。
- 当前阶段新增页面提供上下文接口、键盘路径和关键错误处理。
- 已声明支持的操作系统通过打包验收；未验证的平台不作为已支持发布。
- 未完成的可选能力明确列出，不通过隐藏失败或改变验收含义宣布完成。
- 当前阶段的可选组合在安装/启用时必须满足其验收；未安装时不得成为本地流程的隐式依赖。配置状态、代码版本和数据迁移状态一致且可恢复。

这些是对外发布（分发安装包）的门槛，不是阶段合并的门槛。阶段合并按[开发流程](../dev-rules/development-workflow.md#next-step)只需要 Agent 侧完成和用户授权（A-53）。发布前，用户待办中发布范围内的人工检查要已执行，或者明确列出未验范围并经用户接受。
