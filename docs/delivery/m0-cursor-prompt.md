> 当前范围：以 [已确认决定](../decisions/confirmed-decisions.md) 和 [交付计划](roadmap-and-acceptance.md) 为准。本页保留 M0 工作包；准备状态和历史证据不代表新增目标已经实现。

初轮交付已完成复核。继续当前工作请使用 [M0 收尾 prompt](m0-closure-cursor-prompt.md) 与 [收尾计划](m0-closure-plan.md)；本文保留首次委派的完整背景，不应据此重建工程。

本文是 [M0 执行计划](m0-execution-plan.md)的任务交接文本，状态为 draft。用户将下方文本作为任务提交后，Agent 在该任务的实际授权范围内执行；文件存在不表示 M0 已获验收或技术选型已定稿。

## 使用方式

在本仓库打开 Cursor，先核对其工作目录和现有改动，把下方完整文本作为一次任务提交。默认可以自主选择实验候选和完成全部可执行工作，正式技术定稿留给结果审查；如果用户已明确委派技术定稿，附上原话和范围，Agent 不必重复询问。

如有固定技术偏好、必须支持的合法样本、可用的两个实际卷、人工测试时间或现有外部操作授权，在 prompt 前一次补充。没有补充时按文本默认执行，不阻塞独立原型。完整 M0 退出仍需要真实设备/人工结果和有效决定。

## 可复制文本

```text
你现在是 MANGA 仓库的实施 Agent。请完成下一里程碑 M0「技术与契约验证」的实施、验证、证据整理与审查交接。以 docs/delivery/m0-execution-plan.md 为本次详细任务计划，以 docs/delivery/roadmap-and-acceptance.md 为 POC/AT 和里程碑门槛正本。请实际写代码、运行原型与测试、修复失败，不要只重新给出计划。

一、目标与授权

1. 本次范围是 POC-01—POC-09 和支撑它们的最小验证工程；保持 M1—M4 为后续产品阶段。交付真实可运行的原型、固定样本、故障验证、支持矩阵、选型证据与最终报告。
2. 允许在本地创建/修改所需代码与文档、安装项目依赖、锁定实验版本、生成合成样本、运行受控本地服务、构建 Windows 原型及执行隔离测试。在此范围内自主连续推进，不逐文件或逐测试请求许可。
3. Electron、TypeScript、monorepo 和 Windows 11 x64 是既有方向。后续 A-15 / [ADR-0007](../decisions/0007-technology-stack.md)已正式选择 UI/编辑、SQLite 驱动及工程基础，按该决定实施并补集成证据，不重新要求用户选库。pnpm 正式版本、组合运行时与媒体等未决范围仍需实测推荐和相应决定；不要把实验结果写成产品验收。
4. 仅使用合成数据和独立临时目录；我明确提供的真实样本只读使用。录音只在我主动开始时进行，本地保存，不自动删除或上传。付费模型、真实外站和私有媒体均不是 M0 的默认前置条件。
5. 默认交付本地成果。Git 推送、PR、合并、发布、系统级安装和实际计费/资料上传遵守本次任务已有授权；没有相应授权时完成本地工作并说明具体剩余动作。不要根据仓库历史授权记录推导本次可以公开发布。
6. 本任务以一次委派持续完成为目标，可以有多个内部实施/验证步骤。上下文不足时把真实进展、命令、证据与剩余工作写入交接记录，不丢失状态，不重做已完成工作，不把上下文边界或阶段性演示当作完成。

二、先核查现场与正本

1. 执行 git status --short --branch，保留所有已有改动。继续已有任务分支；如在 main，可按仓库规则新建本地任务分支。不搬动仓库、不重写历史、不覆盖别人的工作。
2. 阅读 AGENTS.md、docs/README.md、docs/delivery/status.md、docs/decisions/open-questions.md、docs/delivery/m0-execution-plan.md，以及 AGENTS 中与本任务相关的产品、架构、数据、Agent、UI、治理、验证和 Git 正本。阅读实际存在的代码；拟议目录和示例类型不等于实现。
3. 核对现有实现与报告。如果已有成果，先验证和复用，再补缺口，不创建平行协议或重复工程。
4. 运行现有 node scripts/verify.mjs。重新探测 Node、包管理器、Electron、媒体工具、原生依赖安装、Windows 打包、实际测试卷和人工设备条件。记下已验证、未核查、不可用；不要把命令存在当作功能通过。
5. 开始即列出工作包 T00—T11、依赖与真实阻塞。只在缺少会改变产品/数据/授权/不可逆结果的决定时问我；其他实现选择与可逆修复继续。缺设备时先完成可自动工作的部分，准备统一人工检查包。

三、工程与共同约束

1. 只创建验证所需的最小 TypeScript monorepo、实验候选、公共契约、Electron 验证宿主和独立宿主。未交付模块不生成空包。记录依赖精确版本、许可、打包影响和替换成本；落选实验不进入生产依赖。
2. 领域层只依赖 MANGA 公开契约；禁止导入 Electron、具体运行时、具体 provider、其他模块私有路径或全局 SQL 连接。建立真实的依赖边界检查。
3. 复用设计正本的命令、上下文、身份、版本、错误、取消、幂等和生命周期语义。输入输出用运行时 schema 校验，调用来源和授权由可信宿主验证。
4. Renderer 无 Node 特权、隔离与沙箱开启，preload 提供窄接口；实际验证 service/UI/worker 的可序列化通信、取消、断连与快照恢复。不能以同进程函数测试替代 IPC 证据。
5. UI 与假 Agent 走同一应用服务，长任务固定目标和输入版本，短事务由数据所有者提交，提交后才发布事件；旧 epoch 或旧修订不能继续写入。
6. 合成样本有 ID、预期、指纹和可重建方式；固定生成输入与工具版本。临时库、录音、生成媒体和凭据不提交。测试数据目录与真实用户目录隔离。
7. 用 docs/templates/module-spec.md 记录实际模块所需深度；公共契约和长期选择保留可追溯决定。同步变更的正本、登记表和导航，不扩大根 AGENTS 为临时任务清单。

四、按依赖完成所有 POC

遵循详细计划的 T00—T11；以下是不可漏掉的重点，不能代替计划中的完整场景：

- POC-01：TXT/EPUB、中日文、emoji、组合字符、重复句、非法容器；Unicode 码点与 DOM UTF-16 映射；改字号/窗口/解析规则/源版本后的精确恢复或明确待修复。
- POC-05：块 ID、选区/撤销、源编辑与布局编辑、循环互嵌/未知对象；真实 Electron 中的中文输入法、键盘、窄窗和高 DPI 检查，提供最终截图与人工步骤。
- POC-06：真实 SQLite 单写入、多窗口 Profile、第二宿主冲突、事务事件、1 万资源/5 万块中日文搜索、范围过滤、备份附件与未知载荷往返、迁移失败恢复、提交边界真实进程终止、Windows 原型打包冒烟。
- POC-04：同一小说核心在两个宿主装配；依赖解析、激活失败、重复/重入释放、50 次启停、共享依赖；提交屏障与旧模块/绑定 epoch 拒绝；UI/假 Agent 同命令、幂等、版本/范围保护和跨进程取消恢复。
- POC-08：两个固定假源的冲突/空值/超时/限流、同名跨媒介/续季歧义、字段来源与用户锁定、换源身份稳定、断网和停用期间编辑、资料包往返。
- POC-09：loopback HTTP、Range/ETag、取消确认、文件名/路径/重定向/配额约束、同名不覆盖、跨卷、磁盘不足、文件发布/记录/入库各边界的真实子进程终止、重复恢复只入库一次；移除下载组合后资料仍可用。用独立有限容量环境或故障注入测磁盘不足，不填满工作盘；模拟与实机分开报告。
- POC-03：固定容器/编码/字幕/音轨/时间基/关键帧样本矩阵；实际播放与后端比较；无转码请求切点与实际输出、同步、变帧率/非零起始时间、不兼容拒绝；记录后端版本和构建条件，支持范围按组合表达。
- POC-02：真实主动麦克风采集，采样偏移/时钟校准，翻页/换资源和暂停/倍速/跳转分段；固定 ASR 夹具的延迟/失败/重试；耳机/外放、设备权限/断开/切换实测。不能用模型返回时刻定位，不能用模拟录音冒充声学验证。
- POC-07：共同 SDK、能力图、故障夹具和三个场景比较运行时候选；required/optional、single/many、显式关闭、Bundle 冲突、多 Facet、结构变化与恢复；记录契约变更/依赖升级/故障诊断成本。先验证必要候选，按证据补充，不能预设胜出或为了比较开发两套完整产品。正式生产只推荐/选择一个实现。

五、验证与证据

1. 为工程建立真实安装、开发、类型/静态/边界检查、测试、样本、性能、打包和报告命令。详细计划中的 node scripts/m0.mjs 各子命令及 node scripts/verify-m0.mjs 是拟议接口，创建并运行后才可写为可用。
2. 根 node scripts/verify.mjs 保留原治理检查并接入新增工程适用的快速门禁。CI 使用锁定依赖和真实检查，保留 repository-quality 身份；Windows 设备与完整打包有独立明确入口。修改 CI 时同步说明与必要配置，未经授权不操作远端 Ruleset。
3. 不使用 --if-present、吞异常、跳过断言、全量 mock 存储或放宽硬性要求来制造成功。门禁变更至少验证一个反例确实返回非零。测试有缺项就明确输出缺项。
4. 性能按照 requirements.md 第 6.2 节，固定机器/构建/数据/查询集/样本量、保存原始测量，报告 p95 等适用统计及冷/热定义。按 A-14 使用当前 Windows 11 参考机，结果不外推其他配置；不能把远程延迟混入本地指标。
5. 为九项 POC 各写版本化报告，包含执行人、commit 与未提交差异/指纹、环境、依赖、样本、步骤、预期/实际、命令、证据和限制。测试成功仅覆盖实际场景，POC 子集不能将完整 AT 标为 passed。
6. 用 not-run/running/passed/failed/blocked 记录实际状态。模拟、真实设备、文件系统和人工检查分开；有必需未测子项时父 POC 不得声称全部通过。保留失败历史，新版本复测新增证据。
7. 人工参与集中到可运行成果之后：提供启动命令、设备/样本要求、逐项操作、预期和结果记录位置。可以一开始告知所需准备；缺少真实操作时先做所有独立工作，再准确交代剩余项目。

六、选型、完成条件与最终交付

5. 汇总报告分别回答：自动化实现/验证是否完成，M0 是否达到正式退出条件，M1 是否满足进入条件。列出每个仍失败/阻塞/未执行项的原因、负责人和下一动作。
6. 只有必需实测、人工结果及 M0 对应决定全部满足，才能写 M0 完成。若还缺设备测试或最终决定，交付完整可审查成果，明确“M0 尚未退出”；继续完成一切不依赖缺项的工作，不把阻塞隐去，也不将半成品称为全部完成。
```
