# 架构、模块与契约开发约束

触发：新增模块/包、改变依赖、进程分工、公共接口或选择基础框架。正本见 [总体架构](../design/architecture.md)、[组合方案](../design/composable-ai-native-architecture.md)、[领域模型](../design/domain-model.md)和 [Agent 协议](../design/agent-and-plugins.md)。本文规定如何落实这些边界，不重写协议。

## 架构检查

| 约束 | 原因 | 验证入口 |
| --- | --- | --- |
| UI、Agent、工作流经同一应用服务，持久修改由数据所有者处理 | 防止同一操作出现不同权限、修订和撤销语义 | AT-09、AT-10 |
| 领域依赖公开契约；平台、模型、运行时和站点类型留在适配器 | 保证停用、替换和独立宿主可行 | AT-21、POC-04 |
| 消费者不导入提供者实现或其他模块私有路径 | 依赖图必须与声明一致 | `node scripts/check-deps.mjs` |
| 进程分工遵循特权、数据所有权和计算负载 | 重型解析不能阻塞 UI，多个写入者不能破坏一致性 | POC-06、AT-17、AT-20 |
| 最小内核只承担约定机制，业务功能可组合 | 不让 kernel/shared 变成隐含业务中心 | POC-07、AT-36—38 |
| 长任务固定输入，短事务提交，完成后发布事件 | 防止远程请求持锁、晚到结果覆盖新修订 | AT-10、AT-17、AT-43 |

确认原则是长期约束；未选型的进程实现、数据库驱动、框架和代码路径按决定台账验证，不把上述检查误作库选择批准。

## 公共接口

公共契约至少明确身份、版本、输入/输出 schema、错误、范围、幂等、取消、副作用和兼容边界。跨进程 DTO 必须可序列化，TypeScript 类型不能替代运行时校验。大媒体使用受控句柄或流，不嵌入无限制 JSON。

修改协议时区分命令版本、服务 API 版本、数据格式版本、资源修订和运行代次；不能共用一个版本号替代这些含义。新增字段要说明缺省值与旧消费者行为，删除/重命名先安排兼容与迁移。示例字段改动同时核对各份设计和实际 schema。

模块交付必须能回答：停用后谁保留数据、哪些工具消失、依赖者如何降级、旧回调如何拒绝、未知对象能否导出。参见 [模块规格模板](../templates/module-spec.md)。

## 选型与引入依赖

已获用户授权的对应技术见 [ADR-0007](../decisions/0007-technology-stack.md)。按该选择接入实际使用方并验证，不重新把已选库列作待用户决定；原型依赖与正式已集成依赖分别记录，新增依赖必须有实际使用方和验证范围。

采用必要底层库前记录它解决的问题、自研边界、许可、体积/打包影响、输入法/样本验证和替换成本。无需为每个小工具建 ADR；公开 SDK、运行时、存储、编辑基础等长期选择需要决定记录。

按[连续执行流程](development-workflow.md#continuous-execution)，已选库的接入和常规实现细节自主推进；未定长期方案先做授权范围内的可逆候选验证，把具体证据和推荐集中交审。编写 ADR 或其 proposed 状态不要求每完成一步便暂停，正式采用所需决定仍须如实保留。

组合运行时按 POC-07 的统一契约与场景验证；生产只选一个实现。基础框架、存储和 Agent SDK 选型必须有需求依据与验证记录。代码升级可重启的边界按已确认阶段设计交付，不额外承诺任意热替换。
