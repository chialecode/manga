# 开发流程与完成标准

适用于实现、修复和文档工作。规则有效性与变更分级见 [文档治理](../governance/documentation-policy.md)。

## 1. 开始条件

实施前明确目标、受影响需求/验收 ID、范围、正本和已知未决事项。局部修复在任务里写清即可；新增模块、跨模块流程或公共契约变化使用 [变更提案](../templates/change-proposal.md)和 [模块规格](../templates/module-spec.md)所需部分。

进入正式产品实现前，相应阶段的 POC 与范围决定需要满足 [交付计划](../delivery/roadmap-and-acceptance.md)的进入条件。技术未知可做隔离原型；原型记录版本、样本、可用范围和删除/保留方式，不把实验代码直接当作最终架构。

按已确认的 Agent 优先顺序，M0 整体未退出时可以先完成 M1a 自身依赖的基础验证与可逆集成；相关安全、生命周期、存储和打包门槛通过后再开放实际 Agent 工具。不能把并行实施许可写成 M1a 进入验证或产品验收已通过，结果见 [M1a 总结](../evidence/m1a-summary.md)。

## 2. 实施与同步

1. 检查现场文件和已有变更，按 AGENTS 读取专题；已有工作区/分支直接复用。
2. 找到同类操作的应用服务、数据所有者和可复用能力，先处理模型和边界，避免增加旁路。
3. 分小步实现正常流程和关键失败路径；公共 API、schema、UI/Agent 调用方与作者文档一起更新。
4. 修改需求或行为时同步其设计、交互、验收映射；只改内部结构且契约不变时说明无需文档变化的理由。
5. 实现中持续运行[质量门禁](quality-gates.md)要求的相关检查；Agent 完成本轮里程碑/明确子阶段并自检后，核对暂存内容，按有效授权保存一个阶段 commit。审查者集中修复后，将未 push 的修复和审查记录 amend 回该阶段提交；一个阶段只有一个提交，已推送后默认追加集中修复。推送批次执行 `node scripts/verify.mjs`。时机按 [Git 工作节奏](git-and-github.md#1-本地优先与工作节奏)，不按内部工作包或时间配额提交。失败先定位，不能删除断言或放宽需求来制造通过。
6. 对最终内容按 [评审口径](../../REVIEW.md)复核，记录证据、当前状态与未决项，再交付。

变更现有有效需求，需要把用户决定回写；技术选型和架构替换用 [ADR](../templates/decision-record.md)。用户已明确授权的范围内无需再为每个文件、每次测试或可逆修复请求批准。

<a id="continuous-execution"></a>
### 2.1 Agent 连续执行与集中审批

默认有两条互不阻塞的流水线（A-53）：Agent 侧是“一次交付任务 → Agent 连续实现、自测和修复 → 保存交付 commit → A 集中审查 → 经用户授权后 push/PR/合并 → 下一阶段”；用户侧是[用户待办](../../USER-ACTIONS.md)，用户在任何阶段逐项确认、解决，两边的交流方式见 [2.3](#agent-user)。用户已明确希望尽量少打断 Agent；计划步骤、工作包、测试轮次、普通进度更新都不是人工审批节点。除任务明确限制外，开发授权覆盖本地常规实现、已选依赖安装、合成测试、文档同步和归属明确的 Git 暂存/commit/目标分支准备。不要把每项操作重新包装成许可问题。

| 情况 | Agent 的处理方式 | 用户参与时点 |
| --- | --- | --- |
| 需求已定，属于常规实现、调试、验证、文档或本地版本保存 | 自主选择符合约束的实现细节，失败先修复，完成后继续下一步 | 最终查看结果与证据 |
| 尚需视觉偏好、技术候选定稿、真实服务配置或人工验收，但可先做可逆实现/受控验证 | 按推荐默认值实现，在用户待办写明“当前默认”、适用边界和证据，完成所有可自动工作，不冒充已获最终决定 | 推荐用户处理，不限阶段；未答复时默认一直有效，以后仍可改 |
| push、PR、合并、发布、真实资料迁移或外部调用需要额外授权 | 先检查会话已有范围；已授权即按范围处理，未授权则先完成本地可审阅成果，在用户待办登记 ACT 项（具体分支、目标与动作） | 用户随时授权；push/PR/合并不以人工检查完成为前提，不挡住无依赖实现 |
| 缺失决定会改变需求、数据语义、授权或产生不可逆结果，且下一步无法合理隔离 | 先做必要诊断和方案，列入用户待办的“阻塞项”并在聊天中明确提出，仅暂停依赖部分；独立部分继续 | 必须在受影响动作前回答，不能以沉默或经过时间当批准 |

为未定方案做可逆验证不等于将其 accepted，也不能用“集中审批”绕过测试失败、安全边界或必需决定。只需用户确认的事项不得阻断开发或绑定为阶段门槛；确实阻塞的问题也不能隐瞒到交付时。外部工具或执行环境硬性要求确认时，说明具体动作、规则来源和原因，保留已完成成果，继续可独立的工作。

实施中的进度更新只报告发现、结果和下一步，不用“是否继续”“是否开始下一包”终止任务。缺少真实凭据/设备时优先完成可控提供者、合成样本与故障测试；人工检查写进用户待办，由用户在任一包含该功能的稳定包上随时执行。新增未选长期基础库、需求变更等仍按其职责正本处理，不能因减少打断而自行改变产品承诺。

需要用户处理的待决定、人工检查、配置和外部授权只维护在根目录的[用户待办](../../USER-ACTIONS.md)；计划、报告和聊天只引用其中的编号与证据，不另列清单，历史快照保留。Agent 侧的非阻塞后续项（LOOP）在[执行状态](../delivery/status.md#followup-loops)，不进入用户待办。条目写法、答复回写与生命周期见 [2.3](#agent-user)；已解决/已授权项不再待批，开发缺口不转嫁给用户。一个授权只覆盖实际列明且获准的动作。无需另建审批系统或逐项文件，人工待测保持真实状态。

<a id="mvp-loop"></a>
#### MVP 与反馈 loop

按 A-39，先交付全软件基本功能 MVP，再基于反馈持续迭代；范围及完整链路见[交付路线](../delivery/roadmap-and-acceptance.md#mvp-loop)。A 的计划覆盖整个阶段（A-46）：一次列出该阶段的全部交付、退出条件与收尾流程，不拆成多批；B 连续完成整个阶段的实现、自测和修复，A 集中复核；人工检查与问题答复不绑定阶段，记在用户待办由用户随时逐项处理（A-53）；不要为纯风格或可隔离的小问题反复交回。必要修复按同类输入/状态不变量处理，不能只消除报告里的固定样本。

基本使用不受阻、无数据/引用/权限/恢复风险且不违背当前必须门禁的问题，可由开发者记录到[执行状态的后续 loop](../delivery/status.md#followup-loops) 并安排后续循环，无需逐项请用户批准。记录影响、可用替代、负责人、触发/截止与复测入口；真正产品取舍另进用户待办的 Q 项。已知核心失败不能靠改成“非阻塞”或删除断言通过；只暂停其依赖功能，其他基本功能继续。没有后继承接的当前必须项由当前阶段完成。MVP 达成和正式阶段验收分别判断，不能把尚缺基本功能延期到 MVP 之后却声称 MVP 完整。

<a id="model-test-config"></a>
#### 本地模型测试配置

开发中的真实模型测试从 Git 忽略的本地环境文件按用途读取配置。现有入口为 `MANGA_TEST_LLM_*`、`MANGA_TEST_ASR_*`、`MANGA_TEST_EMBEDDING_*`，字段使用 `API_BASE_URL`、`API_KEY`、`MODEL_ID`、`PROTOCOL`；其中 `MODEL_ID` 对应接口所需的 model_name/model。当前 LLM 与 ASR 均使用 OpenAI 兼容接口，各自使用独立模型与凭据。文档、示例和测试脚本不硬编码开发者选用的提供者、真实地址或模型作为默认值；历史实测证据中的配置仅描述该次请求。

必要的真实测试开始前先核对对应用途的字段、协议和 URL，不打印密钥或完整环境文件。已提供的配置直接复用；只有本轮必要测试缺少配置时，才向开发者询问该用途的 base_url、api_key、model_name、协议等缺失字段，并说明受阻测试。不要提前索取未来模型，也不要猜测模型、跨用途继承或自动回退；缺配置的真实测试标为 not-run，仅暂停依赖部分，继续受控提供者和合成样本验证。

本地环境配置只服务于明确触发的开发测试，不自动导入桌面 BYOK 设置、不随应用分发、不进入 renderer、日志或公开证据。普通 CI 使用本地受控提供者；真实调用遵守已有测试授权、样本范围和次数预算。原始音频只发送给 ASR，LLM 后续整理仅接收授权转录文本。

<a id="agent-handoff"></a>
### 2.2 Agent A 规划、Agent B 执行、Agent A 审查

这是本项目默认的开发协作方式。A/B 是开发职责，可以对应不同工具或会话；不是产品内 Agent 的权限角色，也不自动授权启动其他 Agent 或向外部工具发送消息。每轮目标是 B 一次完整交付，A 完成集中复核；必要返工不能为减少轮次而隐瞒。

| 环节 | 负责完成 | 交接条件 |
| --- | --- | --- |
| A 制定计划 | 核对代码/决定；涉及选型与通用能力时先查证活跃开源候选及适配边界，再写目标、基线、依赖、数据/授权、验收与人工边界 | 方案带官方来源/查询日期/维护与取舍证据，B 能直接执行；不能凭记忆指定自研或把首次调研留给 B；不依赖隐藏聊天记忆 |
| B 连续执行 | 核对现场、准备或复用基线/分支；完成实现、自检与修复，同步相关正本，保存交付 commit | 提供按任务映射的结果、源码/产物/证据、实际验证和剩余事项；不能只交演示、自述完成或截图 |
| A 集中审查 | 对照同一计划、真实代码和证据核实功能与失败路径；复用有效证据，补必要验证，直接修复明确局部问题 | 能给出本轮结果与阶段判断，并把需要用户的事更新到用户待办；较大缺口才形成一批明确返工任务 |
| 用户处理用户待办 | 按 [2.3](#agent-user) 在任何阶段逐项确认、解决：决定、人工检查、授权 | 不是 A/B 流水线的环节，不阻塞它；有效决定由 A 回写正本，在相同范围继续执行无需重复批准 |

**交接使用仓库文件与 Git 版本。** 每轮默认维护一份计划和一份 B 交付报告；A 在复核后补独立审查记录或明确标识的复核部分。已有同等文档直接复用，不因换 Agent、每次小修或聊天结束另建一套文件。详细用例和需求只引用正本，prompt 负责指向计划、标明角色与本轮动作；不得在多个 prompt 里维护互相冲突的任务版本。[交接模板](../templates/agent-handoff.md)提供最小信息结构，按实际范围删减，不是逐字段审批表。

**A 的计划必须可执行并覆盖整个阶段。** 计划对照路线列出该阶段的全部退出条件及对应工作包；前置未实现的依赖（例如上一子阶段未做的部分）直接并入，不留给“下一批”。对每个工作包给出预期结果、关键失败路径及完成证据，区分已存在命令与需 B 建立的命令；列出当前应保留的修复、暂不实现范围和阶段门槛。上一阶段已合并时，计划同时列出其中间文档与制品的清理清单，规则见[阶段收尾清理](../governance/documentation-policy.md#stage-cleanup)。不把尚未定稿候选写成正式决定，也不把无关未来需求塞入本轮。普通实现细节留给 B；仅存在实质取舍时给出方案与推荐，需要用户决定的写进用户待办并给出 B 先采用的默认值。A 的建议不代替用户授权。

**A 的技术推荐先查证开源。** 按[开源选型规则](architecture-and-contracts.md#open-source-first)核对可用性、活跃维护和目标环境，保存官方依据；先设计集成与替换边界，再评估必须自研的最小部分。库的知名度或旧记忆不等于当前适用；已有证据未受变化影响时可引用，新增选型或维护状态变化时重新查询。B 的运行验证补齐兼容性，不能替代 A 应完成的前期查证。

**B 在开始时自行核对一次现场。** 分支、commit、计划、授权与当前文件兼容时直接连续实施；指纹不同或工作区不干净本身不等于阻塞，先判断差异与归属。仅发现会覆盖他人工作或改变本轮含义的冲突时提出具体问题。实施中发现非阻塞缺项，选择满足现有约束的可逆方案、记录依据并继续；不得降低验收或缩减已确认目标。用户新增指示是本轮变更，回写计划/决定和证据范围后继续，不要求重新启动整个流程。

**B 交付前先完成自审闭环。** 对照计划逐项核实代码存在、主流程与关键错误可运行、数据兼容/恢复有证据、文档准确、必要检查已通过，再保存一次交付提交。自检可以反复进行，但不按测试轮次或每个工作包增加用户审批。交付报告按“任务/需求 → 实现位置 → 验证证据 → 状态与限制”映射；明确 commit、源码指纹、产物位置、命令/退出状态及样本口径。相同源码的已有证据可复用，变化部分重新验证，不复制陈旧通过记录。

报告与实现同次提交时，不为把该报告所在 commit 的哈希写回报告再制造一次提交。报告写测试基点/源码指纹，交付消息提供最终 commit，或从包含该报告的提交解析版本；关键是能对应实际被测源码。

**A 尽量在本轮结束问题。** 审查不是复述 B 报告或无条件全量重跑；先核对版本和必要场景，检查数据、权限与失败路径。范围内且可确定修复的局部问题由 A 直接修复、自测，按 [Git 审查提交规则](git-and-github.md#review-commits) amend 尚未 push 的阶段提交，消息描述最终结果；已推送后默认追加集中修复。涉及较大模块实现、跨层恢复方案或多处耦合缺口，需要 B 连续编码时，A 完成当前可独立审查后一次性交回所有已确认问题；不每发现一条就往返。纯风格建议不形成阻断，新的产品愿望另记后续任务。

**返工只描述差异。** 每条问题使用当前审查报告内稳定编号（如 F-01），写明严重度、触发/实际结果、要求/预期、位置与证据、修复验收。给 B 当前基点、需要保留的 A 修复、完整问题清单与复验范围；不重复整份原计划，也不要求重新建工程。B 逐条回复修复位置和实际验证，无法修复则给具体原因与剩余阻塞；“已处理”不构成关闭证据。A 核实后关闭原编号，不用改名丢失问题历史。

**沟通只传递必要变化。** 实施中的更新说明新发现、已解决问题、实质阻塞和接下来的验证，不用长日志或反复贴计划替代进展；收到状态询问简短回答后继续。最终聊天只需结果、版本、报告/产物入口，以及用户待办中本轮新增或变化的编号，详细证据放仓库。默认每次只有一个 Agent 修改同一工作区；确需并行时明确分工和隔离，不以共享脏工作区提高吞吐。

**工程交付、审查和产品验收分别判断。** 不能把 B 自检通过写成 A 已审核，不能把 A 技术通过写成用户已验收。Agent 侧的阶段完成（必需用例与自动证据通过、A 审查收敛、无阻塞项）与产品验收（人工检查）分开：前者决定能否请求 push/PR/合并，后者在用户待办里独立推进、可晚于合并。只缺真实设备或最终定稿时，可交付代码并列明验收边界；仍缺实现或自动测试时由 Agent 继续，不能包装为人工待办。下一轮 A 以最终审查版本、已关闭问题和有效决定为基线制定计划，避免再次讨论已解决事项。

<a id="agent-user"></a>
### 2.3 Agent 与用户的交流（A-53）

2.2 是 Agent 之间（A ↔ B）的交接方式，本节是 Agent 与用户之间的交流方式。两者分开：A/B 通过计划、交付报告和 Git 版本交接；Agent 与用户只通过根目录的[用户待办](../../USER-ACTIONS.md)和聊天中的编号交流。用户不需要读计划、报告或证据，就能知道自己要做什么。

| 环节 | Agent 做什么 | 用户做什么 |
| --- | --- | --- |
| 登记 | 发现需要用户的事（决定、人工检查、授权、外部配置）时写进用户待办：稳定编号，要做什么，推荐或当前默认，推荐时机，真正受阻的动作（若有），步骤与预期 | 无需立即回应 |
| 继续开发 | 非阻塞项按推荐默认值实现，并在条目里写明“当前默认”；阻塞项只暂停依赖它的部分 | — |
| 推荐 | 在“现在可以做的”里按价值排序；每轮结束的聊天只列本轮新增、变化或需重测的编号 | 任选其中的项处理，可以分多次、跨阶段 |
| 答复 | — | 在对话中回复编号与结果，或在文件“状态”列填写后告诉 Agent |
| 回写 | 决定写入[确认记录](../decisions/confirmed-decisions.md)与职责正本，并调整实现；检查结果写入用户待办和当期证据，失败项转为当前阶段的修复项，修好后标“待复测”；授权按写明的范围执行 | — |
| 结项 | 处理完的项移到“最近处理完的”（保留锚点）或删除；后续改动涉及已通过的检查时，把它标为“需重测” | — |

- **不限定阶段。** 非阻塞项只写推荐时机，不写截止阶段；未处理的项自动顺延，不影响阶段的工程完成、push/PR/合并或下一阶段开工。只有确实依赖它的动作（例如对外分发安装包）才在条目里写明“某动作前必须”。
- **阻塞要满足两个条件。** 缺失决定会改变数据含义、授权范围或造成不可逆结果，并且无法用可逆的默认值隔离。阻塞项列在用户待办的“阻塞项”，同时在聊天中明确提出，只暂停依赖部分。
- **不替用户做。** 未答复不等于同意；默认值照常运行，但不写成用户已确认。人工检查保持 not-run，不由自动脚本代填结果。
- **不转嫁。** 缺代码、可以自动测试的内容由 Agent 完成，不写成人工检查。人工检查只覆盖确实需要人的部分：真实设备、主观体验、真实服务与账户。
- **写到能直接照做。** 启动命令、隔离数据、样本准备、步骤与预期都写在用户待办；聊天和报告只引用编号，不另写一份步骤或待办清单。
- **授权按动作计。** 一个授权只覆盖写明的动作，授权 push 不等于授权合并或发布。

<a id="next-step"></a>
### 2.4 每轮结束必须推荐下一步

每次完成 A 规划、B 执行或 A 审查后，在最终回复中给出一个首选下一步，说明当前角色已完成什么、阶段是否完成、推荐理由及执行条件。不要让用户从长报告自行猜测，也不要以“如需可以继续”代替明确建议。建议不是执行授权，不自动启动另一个 Agent、发送消息或开启新阶段。

| 当前状态 | 首选建议与必须提供的内容 |
| --- | --- |
| A 已完成可执行计划 | 推荐交给 B；附一段可复制 prompt，包含角色、仓库计划入口、分支/基点、连续执行范围、必须保留项、检查和交付要求 |
| B 已完成实现、自检和交付 | 推荐交给 A 集中审查；附审查 prompt、最终版本和报告入口，不把自检通过写成验收通过 |
| A 发现需要跨模块持续编码的缺口 | 推荐交回 B 一次性返工；给稳定问题编号、完整差异和复验入口，保留 A 已修复内容；不把缺代码交给用户人工验收 |
| A 审查收敛（Agent 侧阶段完成） | 推荐用户授权本阶段的 push、创建 PR、合并：在用户待办登记 ACT 项，列明分支、依赖、目标和动作范围，只有用户明确授权后才执行。同时列出用户待办中本轮新增或需重测的编号。人工检查与待决问题不是授权的前提 |
| 远端操作已完成，或用户暂不授权 | 推荐开始下一阶段的 A 规划；说明目标、依赖与首个 A 规划入口。前一阶段未合并时，按 [Git 依赖分支规则](git-and-github.md#11-分支边界与基点)从其阶段提交继续。不以推荐替代用户启动新阶段的指示 |
| 用户答复了用户待办中的事项 | A 回写决定与检查结果；失败项能局部修复的直接修，需要较大编码的交给 B（附 prompt），都在当前阶段内完成 |

人工检查的启动命令、隔离数据位置、合成样本准备、逐步操作、预期结果、故障定位入口和重测边界只写在用户待办，并且要写到用户能直接照做；最终聊天列出编号并链接到该页，不另写一份步骤。开发入口应自动准备匹配 Electron ABI 的原生依赖；已知缺代码先由开发者补齐，不交给用户反复试错。

存在未关闭的 Agent 侧必须项（必需用例或自动证据失败、A 审查未收敛、阻塞项未解决）时，不能推荐合并或直接跳到后继阶段。未执行的人工检查和未答复的非阻塞决定不算未关闭项，它们随用户待办顺延。发布另需对应授权；本地 commit/amend 按既有授权连续处理，不新增审批点。

## 3. 完成标准

| 交付类型 | 必须具备 |
| --- | --- |
| 文档框架/说明 | 正本清楚、状态真实、链接与登记有效、待决问题有归属 |
| 局部功能或修复 | 明确用户可观察结果、相关验证、受影响文档同步、没有未处理的阻断缺陷 |
| 新模块 | 数据/依赖/能力/上下文/生命周期/导出契约，以及相应场景验证 |
| 契约或存储变更 | 版本与兼容策略、迁移和恢复路径、旧数据/调用方样本 |
| UI | 设计依据、完整状态、键盘/输入法路径和与声明范围匹配的界面证据 |
| 阶段（push/PR/合并） | 必需用例与自动证据通过、A 审查收敛、阻塞项为零、用户授权；人工检查的状态如实记录，可以是 not-run 并在用户待办中顺延 |
| 发布（对外分发） | 发布范围内的人工检查已执行，或明确列出未验范围并获用户接受；支持矩阵、打包与恢复验证、剩余限制 |

“文档写好”“接口存在”“按钮出现”“测试命令返回成功”分别只是局部事实。验收完成必须有对应输入、步骤、预期与实际结果，不能用同一次通过记录覆盖变更后的版本。

## 4. 任务交接与例外

未完成时在当前任务或执行台账记录已做内容、下一动作、阻塞原因和有效证据；只有需要长期接续的工作才单独建交接文档。不得把临时记忆写进根 AGENTS。

交接注明分支和已提交版本，以及尚未提交的文件与归属；远端备份只有 push 成功后才能声明。阶段切换先保存已复核基线，再按独立目标建立后继分支；前置尚未合并时按 Git 规则说明依赖，不把无关阶段持续堆在同一未提交工作区。

发现门禁无法执行时说明原因、影响和替代检查，不静默跳过；重要验收仍未执行时不能宣称达到相应发布条件。合理例外要标明对应规则、适用范围、责任人、决定依据、替代验证和失效条件；永久改变规则走正常修订。会话中的授权和已经决定的例外持续有效。
