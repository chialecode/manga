# 第二阶段：高风险验证

> 状态：`authoritative`。本阶段的验收标准是硬门槛，不达标不进入第三阶段。
> 架构依据见 [`docs/architecture.md`](../architecture.md) §21「实施顺序 · 阶段 2」、§2 质量指标、§22 风险与触发器、§24 待验证事项。
> 前置：阶段 1 已验收（PR #1，commit `71dd1ee`），退出条件 E1–E12 全部满足。

## 1. 阶段目标

**在写任何业务代码之前，把三个可能推翻架构选型的假设变成实测结论。**

第二阶段不交付任何用户可见功能，也不交付任何会进入发布产物的代码。它交付的是**结论**：每一条以 ADR 与基准报告的形式固化，成为阶段 3–6 的决策依据。三个假设分别是：

1. **视频**：Chromium `<video>` 对本地动画常见封装/编码组合的支持边界，以及 L2 转封装路径的延迟，决定阶段 6 的播放引擎架构是否成立（风险 R1）。
2. **规模**：trigram FTS5 + better-sqlite3 在 100k 条目下的查询延迟、索引体积与内存占用，决定阶段 3 的数据层设计是否成立（风险 R2、R5）。
3. **崩溃**：真实写入压力（而非阶段 1 的轻负载）下的崩溃一致性，决定扫描/索引管线的事务边界设计是否成立。

**为什么必须现在做**：这三项中任何一项不达标，应对方案都是架构级的（换播放引擎、改索引方案、并进程）。如果先写了阶段 3–6 的业务代码再发现，返工成本以月计。

## 4. 里程碑

### M2.0 · 素材与基准设施

**目标**：可复现的测试素材生成，与统一的基准采集框架。

**关键约束（动手前必读）**：

- 仓库 `vendor-bin` 的 FFmpeg 是 `win64-lgpl-shared` 变体，**不含 libx264 / libx265，无法软编 h264/hevc**。样本生成需要开发机上的独立编码工具链，二选一：
  - **NVENC / QSV / AMF 硬件编码器**（lgpl 构建已含这些接口，但依赖开发机 GPU 支持，hevc-10bit 需要较新的硬件编码器）；
  - **一份仅存在于开发机的全量 GPL FFmpeg**（如 BtbN `win64-gpl`），只用于生成素材，**不 vendor、不入库、不随产品分发**，因此不触发 GPL 义务，也不受依赖准入约束（它不是依赖，是本地工具，等同于开发者机器上的任何 CLI）。生成脚本显式接收其路径参数，绝不回退到 `vendor-bin`。
- 素材体积达 GB 级，**不入 Git**。生成到 gitignore 的 `scripts/fixtures/generated/`；提交的是**生成脚本 + 参数清单 + 产物 sha256 清单**，保证任何机器可复现同一批样本。
- 素材内容全部合成（`testsrc2`、色条、合成音频），**不使用任何真实版权媒体文件**，不访问任何真实站点（闸门 `network-allowlist` 继续生效）。

**交付物**

| 路径 | 内容 |
|---|---|
| `scripts/fixtures/gen-video-samples.mjs` | 15 个样本生成：{mp4, mkv} × {h264, hevc-8bit, hevc-10bit, av1} × {aac, ac3, flac} 取 12 个代表组合，另加 双音轨+三内封字幕 mkv、4K HDR（HDR10 静态元数据）、VFR；每个样本内嵌烧录帧号（seek 误差比对用） |
| `scripts/fixtures/video-samples.manifest.json` | 每个样本的生成参数与 sha256 |
| `scripts/fixtures/gen-library.mjs` | 合成 100k 条目：作品/卷/文件层级、CJK 混合标题（从固定词表组合）、可选正文文本（V8 用） |
| `scripts/fixtures/cjk-search-golden.mjs` | CJK 检索质量黄金用例 ≥ 100 条：中文简繁、日文汉字/假名混写、音译名、缩写，各附期望命中 |
| `scripts/bench/lib/collect.mjs` | 统一采集：P50/P95/P99、进程 PWS、帧时间；输出 JSON 入 `docs/bench/` |

**验收**

- 两台不同机器（或删除产物后重新生成）产出的样本 sha256 一致（编码器版本固定的前提下）。
- `gen-library.mjs` 生成 100k 条目 ≤ 10 min，且两次生成内容一致（固定随机种子）。
- 反例验证：生成脚本在找不到外部编码器时**明确报错退出**，不静默回退到 `vendor-bin` 的 ffmpeg。

**前置**：无。**需要开发者确认**：编码工具链选择（见 §7）。

### M2.1 · 视频能力矩阵实测（V1、V6）

**目标**：15 个样本在 Electron `<video>` 中的实际表现，逐个记录，无一遗漏。

**交付物**

| 路径 | 内容 |
|---|---|
| `scripts/spike/video-matrix/` | 一次性测试页：加载样本、记录 `canplay`/`error`/轨道枚举/`MediaCapabilities.decodingInfo` 结果 |
| `docs/bench/video-matrix-<date>.md` | 矩阵报告：每样本 × {能否播放, 视频轨, 音频轨, 字幕轨可见性, 多音轨切换, HDR 表现, VFR 表现}，标注 Electron 版本与 GPU 型号 |
| `docs/adr/`（新增一条） | V1 结论：哪些组合走 L0 直接播放、哪些必须 L2、哪些彻底不支持 |

**必须回答的问题**

- mkv 容器 Chromium 到底认不认（不同编码下行为是否一致）。
- hevc-8bit / hevc-10bit 的硬解可用性与 `decodingInfo` 的 `powerEfficient` 值（V6，记录 Windows「HEVC 视频扩展」安装与否两种状态——如果可控）。
- 多音轨 mkv：`audioTracks` 是否可枚举、能否切换（预期不能，走 L2，需实证）。
- 内封字幕：`textTracks` 是否暴露（预期不暴露，需实证）。
- 4K HDR：色调映射表现；VFR：时间戳与 seek 行为。

**验收**

- 15/15 样本有记录，无「未测」项。
- V1、V6 的 ADR 提交。

**前置**：M2.0。

### M2.2 · L2 转封装 spike（V2、N10、N11、R1）

**目标**：实测「FFmpeg 转封装 → `<video>` 播放」路径的首帧延迟、seek 延迟与 seek 精度，对 R1 触发器（seek P95 > 2 s）作出判定。

**交付物**

| 路径 | 内容 |
|---|---|
| `scripts/spike/remux/` | 一次性 spike：用 `vendor-bin` 的 ffmpeg（转封装不需要编码器）把 M2.1 中判定为 L2 的样本转为 fMP4，喂给 `<video>`；实现 seek = 重启转封装 @ 目标时间 |
| `scripts/spike/remux/seek-accuracy.mjs` | seek 误差测量：`ffmpeg -ss` 提取参考帧，与 `<video>` seek 后的 canvas 截帧做像素比对（样本内嵌帧号辅助判定） |
| `docs/bench/remux-latency-<date>.md` | 首帧延迟、seek 延迟 P50/P95、seek 误差分布 |
| `docs/adr/`（新增一条） | V2 结论 + L2 架构决策 |

**判定树（写进 ADR）**

- seek P95 ≤ 700 ms：N11 达标，阶段 6 按管道式 L2 实现。
- 700 ms < P95 ≤ 2 s：N11 降级，记录实测值为新基线，阶段 6 按管道式 L2 + 预热优化实现，N11 重估。
- P95 > 2 s（R1 触发）：实测「先转封装到临时文件再播放」路径；仍不可接受则立项评估 libmpv 第四引擎（依赖准入 + ADR，阶段 6 执行）。

**验收**

- 判定树三分支之一有实测依据地选定。
- seek 误差 ≤ 1 帧（N10）在所选路径上成立。

**前置**：M2.1。

## 6. 本阶段明确不做

写下来是为了防止范围蔓延。以下任何一项出现在阶段 2 的 PR 中都应被打回：

- **任何业务功能与任何正式 UI**。`scripts/spike/` 下的原型是一次性代码：不进包构建、不受 UI 设计规则约束、阶段结束后整目录可删（结论已在 ADR 与基准报告中）。
- **不因 spike 引入运行时依赖**。spike 只能使用仓库既有依赖 + Node/Electron/浏览器内建能力。若某方案（如 libmpv）在判定树中被选中，依赖准入与 ADR 在**阶段 6 执行时**再走，本阶段只记录决策。
- **不优化**。本阶段测量现状、给出结论；除非某项指标未达标且降级判定需要（如 R1 的临时文件路径实测），否则不做任何性能优化。
- **不动锚点、不动 schema**。M2.3/M2.4 的灌库走既有 schema；若发现 schema 缺陷，记录到 M2.5 输出，留给阶段 3 以新增 migration 解决（migration 冻结红线继续生效）。
- **不提交任何生成的媒体样本与数据库文件**。Git 里只有脚本、清单与报告。
