## 2. 回放诊断

检查 [renderer.js](../../experiments/m0-desktop/src/renderer/renderer.js) 发现：

1. `MediaRecorder` 输出 `audio/webm;codecs=opus`，以 WebM Blob 直接存储和播放，没有验证文件时长或可寻址范围。
2. `refresh()` 每次替换全部录音列表。笔记自动保存后会调用它，移除正在使用的播放器；再次点击同一录音也会新建播放器。
3. `URL.createObjectURL()` 没有对应释放，反复打开回放会保留 Blob URL。
4. 使用原生 `<audio controls>`，三点菜单由 Chromium 布局与控件策略决定；应用没有独立“导出录音”按钮。用户看到的菜单差异不直接证明附件丢失。

对既有独立包烟测产生的一条合成录音进行了只读检查：ffprobe 查询容器/流时长，再在隔离的 Electron 沙箱窗口中按当前 Blob 加载方式记录 `loadedmetadata` 与静音播放结束后的媒体状态。窗口使用独立临时 Profile，不使用人工复测数据目录。

| 观察点 | 结果 |
| --- | --- |
| 样本 | 13,455 bytes，Opus / 48,000 Hz；指纹见机器记录 |
| ffprobe 容器/流时长 | 未返回 duration 字段 |
| 初次媒体元数据就绪 | `duration = Infinity`，seekable 终点也非有限值 |
| 播放结束 | `duration = 1.14` 秒，seekable 变为 `[0, 1.14]` |

原始结果：[audio-playback-diagnostic.json](m0-review/audio-playback-diagnostic.json)。其中记录样本指纹、被检查 renderer 指纹、Electron 版本与原始观测。这是针对一条合成录音的诊断，未证明所有真实录音都同样异常。它证实当前保存/加载路径可能在播放前没有有限总时长，足以成为必须修复并回归的原因；列表重建是另一个独立缺口。

复现方式：运行现有 package 烟测生成 fake microphone 附件，从本机 `dist/latest-package.json` 指向的烟测 Profile 取 WebM；对该合成样本运行 ffprobe，在同版本 Electron 中用 `audio/webm` Blob 加载，分别记录 `loadedmetadata` 和 `ended` 的 `duration`、`seekable`、`currentTime`。固定回归应接入 [收尾计划](../delivery/m0-closure-plan.md) R1，不依赖临时诊断程序或私人录音。

本轮没有修改应用代码，问题尚未修复。R1 负责时长/拖动进度、显式导出、列表更新与 Blob URL 生命周期，并验证原有录音兼容。

## 3. 里程碑判断

依据 [M0 退出条件](../delivery/roadmap-and-acceptance.md)，当前仍缺定位/编辑的真实 DOM 联测、采集时间映射、实际媒体播放与支持矩阵、多 Facet 运行时证据、元数据包往返、剩余性能测量及正式选型。现有自动化通过与本次人工通过都仅覆盖相应子集，不能直接把九项 POC 或 M0 标成完成。

现有 `m0-review/summary.json` 是本次反馈之前的机器快照，仍包含旧的人工待测说明；不手工伪造其自动生成结果。当前人工事实以本报告为准，后续 R7 将完善人工证据引用和汇总判定。M1—M4 的完整 AT 仍为 not-run；收尾只完成 M0 的最小验证链路，不提前实现后续完整产品。
