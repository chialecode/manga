## 背景和候选

SQLite 驱动：`node:sqlite`、better-sqlite3、sql.js。宿主：单写入文件锁 vs 多连接。数据目录：安装目录、`%LOCALAPPDATA%`、便携目录。

## 决定与理由

**原驱动推荐（已被替代）**：业务库使用 Node 24 `node:sqlite` WAL。当前正式方向采用 SQLite + better-sqlite3 + Drizzle，见 ADR-0007；现有 `node:sqlite` 仅为 M0 实验实现。**已接受的宿主决定**：一个 Profile 一个写入宿主加文件锁，附件走文件系统。独立资料包导出/导入用于可移植业务数据，不等同整个 Profile 备份，禁止覆盖非空目标。

原推荐的实测依据：CJK n-gram 检索、第二宿主冲突、提交前/后真实进程退出、未知模块备份往返、资料包往返与缺提供者仍可读均在原型上自动验证。原先因本机原生重建链与 Electron 重建成本将 better-sqlite3 作为后备；用户后续选择已改变该顺序，原生绑定的构建/打包验证仍必须补齐。sql.js 不作主路径。

**已确认的目录要求**：默认系统文档目录，全部应用生成内容的位置可配置，开发/正式通道分离。具体分区、迁移与启动定位边界见 [领域模型](../design/domain-model.md#112-文件分区)。原固定本地应用数据目录/安装旁自动便携建议已被本次用户决定替代；安装形式仍未决定，不再等待目录产品确认。

验证/测试继续使用独立临时目录，不指向用户库。单写入宿主已定稿，与用户的路径选择分别验证；定稿不代表迁移与恢复验收通过。

## M1a 实证与正式决定

2026-09-19 在 `packages/storage-drizzle` 接入 better-sqlite3 + Drizzle + FTS5，一个 Profile 一个文件锁写入宿主。已测：旧 schema v1 打开并升级、CJK 检索范围过滤、第二宿主冲突、资料包发布中断后保留暂存/冲突文件、凭据只存引用。推荐继续采用单写入宿主；维护成本是原生 ABI/rebuild/asar 与迁移脚本，复杂宿主替换需要重启。2026-09-20 用户已正式接受此方案。完整迁移/恢复尚有阻断问题，见 [M1a 最新验收审查](../evidence/m1a-acceptance-review.md)。

## 后果和实施

正式工程需冻结迁移规则，按 ADR-0007 验证 better-sqlite3 原生绑定、Drizzle 查询/迁移与旧数据库往返；原 `node:sqlite` 打包结果不能证明新驱动通过。目录修改必须按可恢复迁移契约实施，不能据文档决定直接移动用户文件。
