# 文档治理与变更规则

本文管理 MANGA 的文档权威、职责、更新与证据。适用于 AI Agent 和程序员，2026-09-19 随本次文档框架建立生效。它规范开发过程，不表示所有产品细节已经确认或实现。

## 1. 文档分层与唯一正本

| 层 | 路径 / 正本 | 回答什么 | 不承担什么 |
| --- | --- | --- | --- |
| 入口 | 根 README、AGENTS、CONTRIBUTING、DESIGN、REVIEW | 如何理解、工作和评审 | 不重复维护专项协议 |
| 治理 | 本文、[登记表](document-registry.json) | 状态、负责人、权威范围与更新规则 | 不直接决定产品功能 |
| 产品规则 | [产品原则](../product-rules/core-product-principles.md) | 已确认的长期产品承诺 | 不存未决定的库与技术细节 |
| 需求 | [requirements.md](../product/requirements.md) | 需求 ID、具体行为、阶段范围 | 不宣称实现完成 |
| 设计 | `docs/design/` | 架构、领域、命令、组合、来源和交互方案 | 不把示例代码当实际 SDK |
| 开发与设计规则 | `docs/dev-rules/`、`docs/design-rules/` | 实施、验证、视觉治理的约束 | 不复制全部详细设计 |
| 决策 | [决定与问题台账](../decisions/open-questions.md)、`docs/decisions/` | 确认、假设、选择理由和替代关系 | 不成为第二份接口正文 |
| 交付 | [路线与验收](../delivery/roadmap-and-acceptance.md)、[执行状态](../delivery/status.md) | 定义用例与阶段门槛；汇总实际完成状态 | 不在计划表中伪造执行结果 |
| 验证证据 | `docs/evidence/` | 某个版本上观察到什么 | 不自动升级为约束 |
| 模板 | `docs/templates/`、PR 模板 | 新变更必需信息 | 不代表已有模块或已通过报告 |

同一事实只有一个维护位置。登记表管理文档元数据；需求正文管理需求定义；交付矩阵管理需求到 AT 的映射；执行状态链接证据；决策记录解释选择并链接已经更新的正本。索引、入口和专题规则可以摘要引用，不另存一份数值、状态机或字段列表。

后续开发按以下关系维护文档，是否单独建提案或 ADR 取决于第 5 节的变更规模：

```mermaid
flowchart LR
    Task[用户任务与有效决定] --> Req[需求与阶段范围]
    Req --> Spec[详细设计与模块契约]
    Spec --> Work[实现与相关文档同步]
    Work --> Verify[对应 POC / AT 与检查]
    Verify --> Evidence[版本化执行证据]
    Evidence --> Status[当前状态与发布判断]
    Evidence -->|发现需求或设计问题| Task
```

产品具体要求以需求正本的有效决定为准；基础数据语义归领域模型，命令/上下文归 Agent 协议，组合解析/生命周期细化归组合方案，外部身份/字段策略/获取恢复归外部扩展，页面流程和候选视觉参数归交互设计。专项约束可以细化，不得与上位有效决定矛盾。

## 2. 状态、责任与登记

[document-registry.json](document-registry.json)登记所有仓库自有 Markdown（根目录、`docs`、`.github`，以及以后新增的模块说明），不登记依赖、第三方 vendor 或生成输出。每项包含 `path`、`kind`、`status`、`owner`、`scope`、`reviewed`、`basis`，被替代文档增加 `supersededBy`。

| 状态 | 含义 |
| --- | --- |
| `active` | 在明确 scope 内当前生效；索引和模板 active 只表示应使用该入口/格式 |
| `draft` | 候选需求、计划或设计；可用于已授权原型，未决项不能据此宣称用户已经批准 |
| `reference` | 研究或执行证据；报告只对其版本、环境和范围有效 |
| `superseded` | 已被另一文档替代；保留历史说明和新正本链接，不再作实现依据 |

文档状态与实现状态正交：`active` 不代表代码存在，`draft` 也可能有局部已确认内容。既有评审稿不整篇升级；已确认部分在产品规则/决定台账中列明，未确认部分继续标记。数字版本属于各文档自身，不要求全仓统一递增。

负责人使用角色：产品负责人（当前需求提出者）、技术负责人（当前维护者）、设计负责人、质量负责人、文档维护者。角色尚未分配专人时由当前维护者承担协调；这不是已任命某个人的声明。AI 可以撰写、验证和提出技术方案，不能捏造人的产品确认或验收签字。

`reviewed` 是最近内容核对日期，不是审批日期或自动刷新时间。`basis` 写明依据的需求、决定或任务；禁止用“已批准”替代可追溯依据。每次里程碑进入/退出、公开契约变更、发现冲突或依赖关键版本变化时复核相关文档；无需每次任务全量重审。

## 3. 规范用词与编号

- **必须 / 不得**：适用范围内的硬约束。需求的“必须”按其交付阶段执行，不能把 M4 能力强塞进 M1。
- **应当**：默认规则；偏离要说明理由、影响与验证方式。
- **可以 / 建议 / 假设**：可选或待定，不能当作已经确认的发布承诺。
- 需求沿用 `BASE-01` 等业务前缀，验收沿用 `AT-xx`，技术验证沿用 `POC-xx`；编号不复用、不为排序改号。
- 待决问题 `Q-xx`，既有假设 `A-xx` 保留映射，架构/治理决定 `ADR-0001` 起，跨模块提案 `CHG-YYYYMMDD-简短名称`，验证报告 `EV-YYYYMMDD-简短名称`。
- 新用例必须可复现：前提、操作、预期、失败边界；实际结果另放证据。不把目标性能写成已测性能。
- 规则应写清触发条件、责任范围、约束理由、验证方式；必要时列出例外。没有可判断结果的口号不作为门禁。

## 4. 冲突与未决事项

1. 执行环境与当前任务的有效指令先于仓库约定；当前用户的明确变更可修订历史产品决定，应回写正本和决定台账，不以旧文档阻止已授权工作。
2. 仓库内部按职责找正本和已记录的有效决定，不按文件修改时间、层级深浅或措辞强硬程度猜测优先级。嵌套 AGENTS 仅对其子树补充要求。
3. 文档与代码冲突：代码说明实际行为，需求/契约说明应有行为。判断是实现缺陷、过期文档还是待定需求；不能默认让代码覆盖承诺，也不能按过期文档猜测命令。
4. 两份正本有矛盾时登记问题、列出影响；可明确推导的技术修复直接继续，只有真正影响产品取舍、数据语义或授权的选择才向用户询问。已获授权无需再问。
5. 未决问题写入台账，注明临时假设、依据、决定负责人、截止阶段和被阻塞的具体工作。不受影响的文档、原型和实现继续推进；“等待用户”不能成为暂停全项目的默认状态。
6. 规则、职责、工具与流程均以 MANGA 的有效需求和实际状态为依据，不把尚未建立的机制写成既成事实。

## 5. 变更规模与同步要求

| 变更 | 最小材料 | 同步与复核 |
| --- | --- | --- |
| 错字、链接、措辞清晰化 | 直接改正本 | 文档检查；无需 ADR、新提案或产品确认 |
| 既有范围内的局部实现/修复 | 任务目标、需求/用例 ID、实际检查 | 受影响文档有事实变化才更新；没变化写理由 |
| 新功能或跨模块行为 | 使用变更提案；可以是同等完整的任务/PR 描述 | 需求→设计/模块规格→验收映射→执行证据 |
| 公共契约、技术选型、数据格式或长期规则 | ADR 或同等可追溯决定，加兼容与恢复说明 | 更新唯一正本、使用方、迁移、测试与作者文档 |
| 主题、组件或交互调整 | 引用设计依据、目标状态与验证范围 | 更新设计正本；需产品取舍时记录决定；提交真实界面证据 |
| 重大方案替换 | 新方案、替代关系、迁移与未解决问题 | 旧文档标 superseded，索引和所有入链改指新正本 |

一项变更不必创建全部模板。少量信息能在原任务或 PR 写清时直接写；仅会被后续工作复用的方案或长期决定才单独建档。纯文档治理不要求伪造业务需求 ID。

## 6. 新建、移动、废弃与经验回写

新文档放入职责目录，补登记表和至少一个相关导航入口。跨目录规则在根 AGENTS 增加触发项；模块专用说明放模块附近。不要把临时讨论倾倒成根目录新规范。

文档直接说明 MANGA 的目标、契约、选择理由和验证结果，设计依据应能在本项目的需求、决定与证据中追溯。文件链接和示例使用仓库相对路径或可移植配置变量，不记录个人机器的绝对目录、用户目录、临时文件位置或工作区副本位置。

移动文档时修正全部链接和锚点；有外部稳定入口时保留短跳转文件。取代决定保持旧记录、写明替代者和原因；独立 ADR 编号不改号复用。历史证据保留其原结论，后续更正用新报告链接，不把旧失败改成当时已通过。

排障发现规则错误就修原文，入口遗漏就补入口，能自动验证的回归补到适当测试。一次环境问题先记录为证据，不自动变成全仓永久禁令。完成事项回到状态台账，长期规则不堆积待办。

## 7. 机械检查与人工判断

文档变更运行 [文档检查](../dev-rules/quality-gates.md)。检查覆盖登记、相对链接、锚点、编号和需求到验收映射。语义冲突、用户确认真实性、任务授权、平台支持和证据质量仍需人工/Agent 核对。

本地与 CI 共用 `node scripts/verify.mjs`，文档检查是其中一部分。触发范围、实际覆盖与失败处理见 [质量门禁](../dev-rules/quality-gates.md)；GitHub 设置与 Ruleset 的配置文件、应用和核验按 [Git 与 GitHub](../dev-rules/git-and-github.md)分别处理，不能只在文档中写“CI 会检查”。
