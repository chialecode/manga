# 文档治理与变更规则

本文管理 MANGA 的文档权威、职责、更新与证据。适用于 AI Agent 和程序员，2026-09-19 随本次文档框架建立生效。它规范开发过程，不表示所有产品细节已经确认或实现。

## 1. 文档分层与唯一正本

| 层 | 路径 / 正本 | 回答什么 | 不承担什么 |
| --- | --- | --- | --- |
| 入口 | 根 README、AGENTS、CONTRIBUTING、DESIGN、REVIEW | 如何理解、工作和评审 | 不重复维护专项协议 |
| 用户事项 | 根目录 [USER-ACTIONS.md](../../USER-ACTIONS.md)（用户待办） | 用户需要做的全部事：待决定（含当前默认）、人工检查（含步骤）、授权与外部配置；Agent 与用户只经它和编号交流（A-53） | 不放 Agent 侧后续项、实施计划或证据正文 |
| 治理 | 本文、[登记表](document-registry.json) | 状态、负责人、权威范围与更新规则 | 不直接决定产品功能 |
| 产品规则 | [产品原则](../product-rules/core-product-principles.md) | 已确认的长期产品承诺 | 不存未决定的库与技术细节 |
| 需求 | [requirements.md](../product/requirements.md) | 需求 ID、具体行为、阶段范围 | 不宣称实现完成 |
| 设计 | `docs/design/` | 架构、领域、命令、组合、来源和交互方案 | 不把示例代码当实际 SDK |
| 开发与设计规则 | `docs/dev-rules/`、`docs/design-rules/` | 实施、验证、视觉治理的约束 | 不复制全部详细设计 |
| 决策 | `docs/decisions/`（[确认记录](../decisions/confirmed-decisions.md)、ADR） | 已确认的决定、理由和替代关系 | 不存仍待用户处理的事项；不成为第二份接口正文或实施计划 |
| 交付 | [路线与验收](../delivery/roadmap-and-acceptance.md)、[执行状态](../delivery/status.md) | 定义用例与阶段门槛；汇总实际完成状态 | 不在计划表中伪造执行结果 |
| 验证证据 | `docs/evidence/` | 某个版本上观察到什么 | 不自动升级为约束 |
| 模板 | `docs/templates/`、PR 模板 | 新变更必需信息 | 不代表已有模块或已通过报告 |

同一事实只有一个维护位置。登记表管理文档元数据；需求正文管理需求定义；交付矩阵管理需求到 AT 的映射；执行状态链接证据；决策记录解释选择并链接已经更新的正本。索引、入口和专题规则可以摘要引用，不另存一份数值、状态机或字段列表。

后续开发按以下关系维护文档，是否单独建提案或 ADR 取决于第 5 节的变更规模：

```mermaid
flowchart LR
    Task[用户任务与有效决定] --> Req[需求与阶段范围]
    Req --> Spec[详细设计与模块契约]
    Spec --> Work[实现与相关文档同步]
    Work --> Verify[对应 POC / AT 与检查]
    Verify --> Evidence[版本化执行证据]
    Evidence --> Status[当前状态与发布判断]
    Evidence -->|发现需求或设计问题| Task
```

产品具体要求以需求正本的有效决定为准；基础数据语义归领域模型，命令/上下文归 Agent 协议，组合解析/生命周期细化归组合方案，外部身份/字段策略/获取恢复归外部扩展，页面流程和候选视觉参数归交互设计。专项约束可以细化，不得与上位有效决定矛盾。

## 2. 状态、责任与登记

[document-registry.json](document-registry.json)登记所有仓库自有 Markdown（根目录、`docs`、`.github`、`experiments` 说明，以及以后新增的模块说明），不登记依赖、第三方 vendor 或生成输出。每项包含 `path`、`kind`、`status`、`owner`、`scope`、`reviewed`、`basis`，被替代文档增加 `supersededBy`。

| 状态 | 含义 |
| --- | --- |
| `active` | 在明确 scope 内当前生效；索引和模板 active 只表示应使用该入口/格式 |
| `draft` | 候选需求、计划或设计；可用于已授权原型，未决项不能据此宣称用户已经批准 |
| `reference` | 研究或执行证据；报告只对其版本、环境和范围有效 |
| `superseded` | 已被另一文档替代；保留历史说明和新正本链接，不再作实现依据 |

文档状态与实现状态正交：`active` 不代表代码存在，`draft` 也可能有局部已确认内容。既有评审稿不整篇升级；已确认部分在产品规则/决定台账中列明，未确认部分继续标记。数字版本属于各文档自身，不要求全仓统一递增。

负责人使用角色：产品负责人（当前需求提出者）、技术负责人（当前维护者）、设计负责人、质量负责人、文档维护者。角色尚未分配专人时由当前维护者承担协调；这不是已任命某个人的声明。AI 可以撰写、验证和提出技术方案，不能捏造人的产品确认或验收签字。

`reviewed` 是最近内容核对日期，不是审批日期或自动刷新时间。`basis` 写明依据的需求、决定或任务；禁止用“已批准”替代可追溯依据。每次里程碑进入/退出、公开契约变更、发现冲突或依赖关键版本变化时复核相关文档；无需每次任务全量重审。

## 3. 规范用词与编号

- **必须 / 不得**：适用范围内的硬约束。需求的“必须”在它被排进的阶段执行；不能把待实现的能力写成已实现，也不能把后面才排的能力硬塞进当前阶段。
- **应当**：默认规则；偏离要说明理由、影响与验证方式。
- **可以 / 建议 / 假设**：可选或待定，不能当作已经确认的发布承诺。
- 需求沿用 `BASE-01` 等业务前缀，验收沿用 `AT-xx`，技术验证沿用 `POC-xx`；编号不复用、不为排序改号。
- 待决问题 `Q-xx`、授权/配置/外部动作 `ACT-xx` 与人工检查 `H-xx` 在用户待办维护（编号不带阶段，A-57），Agent 侧的非阻塞后续项 `LOOP-xx` 在[执行状态](../delivery/status.md#followup-loops)维护，编号均不复用；既有假设/确认 `A-xx` 保留映射，架构/治理决定 `ADR-0001` 起，跨模块提案 `CHG-YYYYMMDD-简短名称`，验证报告 `EV-YYYYMMDD-简短名称`。
- 新用例必须可复现：前提、操作、预期、失败边界；实际结果另放证据。不把目标性能写成已测性能。
- 规则应写清触发条件、责任范围、约束理由、验证方式；必要时列出例外。没有可判断结果的口号不作为门禁。

## 4. 冲突与未决事项

1. 执行环境与当前任务的有效指令先于仓库约定；当前用户的明确变更可修订历史产品决定，应回写正本和决定台账，不以旧文档阻止已授权工作。
2. 仓库内部按职责找正本和已记录的有效决定，不按文件修改时间、层级深浅或措辞强硬程度猜测优先级。嵌套 AGENTS 仅对其子树补充要求。
3. 文档与代码冲突：代码说明实际行为，需求/契约说明应有行为。判断是实现缺陷、过期文档还是待定需求；不能默认让代码覆盖承诺，也不能按过期文档猜测命令。
4. 两份正本有矛盾时登记问题、列出影响；可明确推导的技术修复直接继续，只有真正影响产品取舍、数据语义或授权的选择才向用户询问。已获授权无需再问。
5. 尚需用户决定、人工检查、配置或外部授权统一写入 [USER-ACTIONS.md](../../USER-ACTIONS.md)，注明当前默认、依据、推荐时机，以及确实受阻的动作（若有）；不写截止阶段，未处理的顺延（A-53）。报告引用编号，不维护竞争清单。非阻塞缺陷/改进以执行状态中的 LOOP 项承接，实施细节仍在唯一计划。已授权工作继续，“等待用户”不能成为暂停开发的默认状态。
6. 规则、职责、工具与流程均以 MANGA 的有效需求和实际状态为依据，不把尚未建立的机制写成既成事实。

用户已确定采用 Agent 连续开发、集中审批的协作方式，具体执行以[开发流程](../dev-rules/development-workflow.md#continuous-execution)为正本。提案、ADR、模块规格是记录和审查材料，其文件名或 draft/proposed 状态本身不产生逐项许可节点。能在授权范围内以可逆实现获得证据的先继续，非阻塞决定按推荐默认值实施并记入用户待办，由用户在任何阶段确认；只有确实影响需求、数据语义、授权或不可逆动作、且无法用可逆默认值隔离的缺失决定，才列为阻塞项提前询问，并只暂停依赖部分。Agent 与用户的交流方式见[开发流程 2.3](../dev-rules/development-workflow.md#agent-user)。

## 5. 变更规模与同步要求

| 变更 | 最小材料 | 同步与复核 |
| --- | --- | --- |
| 错字、链接、措辞清晰化 | 直接改正本 | 文档检查；无需 ADR、新提案或产品确认 |
| 既有范围内的局部实现/修复 | 任务目标、需求/用例 ID、实际检查 | 受影响文档有事实变化才更新；没变化写理由 |
| 新功能或跨模块行为 | 使用变更提案；可以是同等完整的任务/PR 描述 | 需求→设计/模块规格→验收映射→执行证据 |
| 公共契约、技术选型、数据格式或长期规则 | ADR 或同等可追溯决定，加兼容与恢复说明 | 更新唯一正本、使用方、迁移、测试与作者文档 |
| 主题、组件或交互调整 | 引用设计依据、目标状态与验证范围 | 更新设计正本；需产品取舍时记录决定；提交真实界面证据 |
| 重大方案替换 | 新方案、替代关系、迁移与未解决问题 | 旧文档标 superseded，索引和所有入链改指新正本 |

一项变更不必创建全部模板。少量信息能在原任务或 PR 写清时直接写；仅会被后续工作复用的方案或长期决定才单独建档。纯文档治理不要求伪造业务需求 ID。

## 6. 新建、移动、废弃与经验回写

新文档放入职责目录，补登记表和至少一个相关导航入口。跨目录规则在根 AGENTS 增加触发项；模块专用说明放模块附近。不要把临时讨论倾倒成根目录新规范。

文档直接说明 MANGA 的目标、契约、选择理由和验证结果，设计依据应能在本项目的需求、决定与证据中追溯。文件链接和示例使用仓库相对路径或可移植配置变量，不记录个人机器的绝对目录、用户目录、临时文件位置或工作区副本位置。

移动文档时修正全部链接和锚点；有外部稳定入口时保留短跳转文件。取代决定保持旧记录、写明替代者和原因；独立 ADR 编号不改号复用。历史证据保留其原结论，后续更正用新报告链接，不把旧失败改成当时已通过。已合并阶段的过程文档和制品按[第 8 节](#stage-cleanup)在下一阶段提炼与删除，归档以 Git 合并提交为准。

排障发现规则错误就修原文，入口遗漏就补入口，能自动验证的回归补到适当测试。一次环境问题先记录为证据，不自动变成全仓永久禁令。完成事项回到状态台账，长期规则不堆积待办。

公开内容只描述 MANGA 的目标、技术选择和验证，不记录外部工程的参考、对照或迁移来源关系，也不保留对应名称、目录和源码核查快照。第三方库名称、官方协议文档与必须保留的法律声明属于实现/许可证依据，不属于参考工程叙述。

公开前检查文件名、正文、JSON 证据、配置、生成报告及暂存版本；清理私密材料、密钥、账户/设备标识、个人绝对路径和专属环境细节。使用仓库相对路径、平台目录接口、环境变量和合成样本。历史证据脱敏时标注范围和日期，保留原测试状态、测量与源指纹，不冒充重新运行；脱敏前记录保存在仓库外。

## 7. 机械检查与人工判断

文档变更运行 [文档检查](../dev-rules/quality-gates.md)。检查覆盖登记、相对链接、锚点、编号和需求到验收映射。语义冲突、用户确认真实性、任务授权、平台支持和证据质量仍需人工/Agent 核对。

本地与 CI 共用 `node scripts/verify.mjs`，文档检查是其中一部分。触发范围、实际覆盖与失败处理见 [质量门禁](../dev-rules/quality-gates.md)；GitHub 设置与 Ruleset 的配置文件、应用和核验按 [Git 与 GitHub](../dev-rules/git-and-github.md)分别处理，不能只在文档中写“CI 会检查”。

## 8. 阶段开始的整理（A-45、A-56、A-57）

每个新阶段开始时整理两件事：

1. **无用的文件**，不论是否纳入 Git。逐个按内容决定：原样保留、精炼、提炼有用部分后删除，或直接删除（[8.4 节](#file-cleanup)）。上一阶段已合并的过程文档与制品是其中最主要的一类。
2. **文档里以前阶段的标签**（[8.3 节](#destaging)）。

是否纳入 Git 不决定去留。`.env.local` 不入库，但必须保留；已入库的过程文档，在下一阶段就成了要提炼后删除的内容。目的是让工作树和文档只说明两件事：现在已实现什么，接下来准备实现什么。过去的东西留在 Git 历史里，不在工作树里堆积。

### 8.1 触发与执行人

1. 一个阶段的 PR 合并进 main 后，下一阶段的 A 计划必须列出整理清单：路径或目录、是否入库、内容判断、处理方式和提炼去向。A 盘点时同时看 `git ls-files` 和 `git status --short --ignored`（不含 `node_modules`）。
2. B 在下一阶段分支上执行整理，作为该阶段唯一阶段提交的一部分；A 审查时核对。除非用户另有要求，不单开清理分支或 PR。
3. 不入库的文件整理后仍不入库；从中提炼出的内容要入库时，先按第 6 节的公开规则去掉私人信息和本机路径。B 在报告的“整理记录”里写明不入库文件各类别的数量、大小和处理结果，不写私人材料的名称。
4. 删除已入库的内容前，用 `git merge-base --is-ancestor <合并提交> origin/main` 确认它已在 main 历史中。当前阶段的过程证据在本阶段 PR 合并前不删，审查和返工还要用。

### 8.2 处理原则

- **Git 历史即归档。** 已合并阶段的文件都留在合并提交里。需要回看时用固定链接 `https://github.com/chialecode/manga/tree/<合并提交>/<路径>`，工作树不再保留副本。
- **先提炼、改入链，再删除。** 仍有效的结论、决定、未关闭事项、用户反馈和测量数值，先写入对应正本，再把入链改指正本或固定链接，最后删除。文档检查必须通过。
- **不按阶段保留总结。** 提炼去向都是不分阶段的正本：
  - [执行状态](../delivery/status.md)：已实现的能力、验证状态、已知限制、遗留编号；
  - [确认记录](../decisions/confirmed-decisions.md)与 ADR：决定；
  - [交付路线](../delivery/roadmap-and-acceptance.md)：待实现的范围与验收；
  - [用户待办](../../USER-ACTIONS.md)：需要用户做的事；
  - `docs/evidence/gate/`：最近一次阶段门禁的证据。
- **状态不升不降。** 提炼时保留原状态与范围：passed 仍限定被测版本和子集，failed、not-run、blocked 原样写明，不把历史失败写成通过，也不把未测写成已测。

<a id="destaging"></a>
### 8.3 去掉以前阶段的标签（A-57）

新阶段开始后，文档不再用以前阶段的标签（里程碑编号）来描述任何东西。对当前开发来说，一个决定、功能或问题出自哪个阶段并不重要，文档只区分两种状态：

- **已实现**：现在的产品里有，附验证状态与证据；
- **待实现**：当前阶段正在做的，或以后要做的。

具体做法：

| 对象 | 做法 |
| --- | --- |
| 需求与追踪矩阵 | “阶段”列改为“状态”：已实现、本阶段、待实现 |
| 交付路线 | 不再保留各阶段的里程碑行和阶段小节。改为“已实现能力”的简表（链接执行状态）、“当前阶段”和“待实现” |
| 确认记录与 ADR | 编号保留；描述去掉阶段说法，需要时间时写日期或提交。ADR 文件名不带阶段标签 |
| 用户待办 | 人工检查编号统一为 `H-xx`，不带阶段；适用版本写提交或稳定包的生成日期 |
| 执行状态 | 不按阶段列行；只写已实现能力、当前阶段和后续 loop |
| 路径、命令与目录 | 使用不带阶段的名字，例如 `node scripts/stage.mjs <命令>`、`docs/evidence/gate/`、`dist/samples/<类别>` |
| 代码注释与测试名 | 同样适用。描述历史的说法删除，或改写成对当前行为的说明 |

例外：

- 当前阶段的名称可以出现。它代表正在做、尚未完成的工作，出现在当前阶段的计划、报告，以及执行状态与交付路线描述当前阶段的地方。
- 当前阶段的计划与报告要列出整理清单，可以写以前阶段的路径和标签；它们本身在下一阶段开始时被改写或删除。
- Git 提交信息、PR 标题与正文是历史记录，不是文档，不改写。
- 固定归档链接（`https://github.com/<所有者>/<仓库>/tree|blob/<提交>/<路径>`）指向只存在于历史中的文件，链接里的路径可以带标签；链接文字和周围的说明不可以。

机械检查：`scripts/check-docs.mjs` 拒绝登记文档中出现 `currentStage` 以外的阶段标签；当前阶段的计划与报告（登记表里 `retireAfter` 等于 `currentStage` 的文档）和阶段门禁的原始证据不在检查范围内；`m4a`、`m4v` 这类格式名和固定归档链接里的路径不算阶段标签。阶段切换时先更新 `currentStage`，以前的标签随即全部报错，这就是执行本节整理的提醒。

### 8.4 按内容整理文件（A-45、A-56）

范围是整个工作区：已入库的文件（`git ls-files`）和不入库的文件（`git status --short --ignored`，不含 `node_modules`）。逐个看内容，回答两个问题：现在还有没有使用方（代码、脚本、测试、文档入链或用户）；里面有没有仍有效的内容。再选一种处理：

| 处理 | 适用 | 做法 |
| --- | --- | --- |
| 原样保留 | 仍在用，内容都有效 | 不动 |
| 精炼 | 文件仍需要，但有一部分过时 | 删去过时部分，只留当前有效的内容；名字带以前阶段标签或返工轮次的，改成按能力命名，入链同步 |
| 提炼后删除 | 文件不再需要，但有一部分仍有效 | 先把有效部分写进去处（正本、按能力命名的测试或通用脚本），改好入链，再删除 |
| 删除 | 没有使用方，也没有仍有效的内容 | 删除 |

常见内容的默认判断如下。实际处理以核对内容为准，不按目录一刀切：

| 内容 | 入库 | 默认处理 | 提炼去向 |
| --- | --- | --- | --- |
| `.env.local` | 否 | 保留。需要精炼时（已没有使用方的变量、需要新增的变量），Agent 按键名列进用户待办，用户同意后再改；不读取、不输出与任务无关的值 | — |
| Profile 与用户数据目录（包括用户做人工检查时在用的独立资料）、用户提供的参考材料 | 否 | 保留不动。放置位置不安全时（例如在 `dist/` 下），在用户待办里建议移动，用户同意前不动 | — |
| 固定版本的工具（`dist/tools`）、生成的合成样本、人工检查正在用的最新稳定包 | 否 | 保留；其中的下载日志与旧版本删除。目录名带阶段标签的，随脚本一起改名 | — |
| 长期正本：入口文档、用户待办、需求、设计、规则、决定/ADR、路线、状态、模块规格、模板 | 是 | 精炼：删去按轮次追加的过程叙述、旧 SHA 流水账和以前阶段的标签，只留当前结论与链接 | — |
| 阶段计划与报告：`docs/delivery/stage-plan.md`、`docs/delivery/stage-report.md` 及其中的交接 prompt | 是 | 下一阶段的 A 计划改写 `stage-plan.md`；报告提炼后删除，由 B 为新阶段重建 | 决定 → 确认记录/ADR；验收定义 → 路线；需要用户的事 → 用户待办；Agent 侧未完成项 → 后续 loop 或新计划；结果 → 执行状态 |
| 轮次证据：运行目录里的截图、JSON、样本副本 | 都有 | 入库的只留 `docs/evidence/gate/` 里最近一次门禁的结果，其余删除；执行状态引用的数值先抄进执行状态 | 执行状态、固定链接 |
| 探针脚本、复现用例、一次性审查脚本、按轮次命名的测试与模块 | 都有 | 发现过缺陷、仍有价值的断言迁入按能力命名的回归测试；仍在用的模块与通用工具改成按能力命名；其余删除 | 迁移映射写进整理记录 |
| 原型，以及只被原型或已删脚本使用的依赖与配置 | 是 | 产品已替代、门禁不再使用的删除；仍承担验证的保留，并在仓库地图写退出条件 | 仓库地图 |
| 生产代码中的测试装置：主进程里的打包烟测、审查钩子 | 是 | 移到只在测试入口加载的位置，行为不变 | — |
| 日志、旧安装包、构建缓存（如 `apps/desktop/.vite`）、性能剖析输出、草稿脚本、提交与 PR 草稿 | 否 | 删除 | — |

不得删除：用户数据与 Profile、`.env.local`、许可证和第三方声明、ADR（被替代的保持 superseded）、确认记录、仍被测试使用的合成样本（可移到测试夹具目录）。用户待办或执行状态仍引用、尚未提炼的依据，先提炼再删。拿不准的先在用户待办里问，不删。不得用跨目录的通配命令清理，以免误删 Profile。

### 8.5 整理记录与审查

当前阶段报告末尾附“整理记录”，内容包括：

- 删除与精炼的路径（可按目录写）、理由、提炼去向和归档提交；
- 测试、脚本与模块的迁移映射（旧文件 → 新文件，或删除理由）；
- 不入库文件的处理汇总：各类别的数量、大小和处理结果。

测试数量下降必须由映射解释，不能用删除断言换取通过。A 审查抽查被删内容里有没有仍需要的结论遗失，并确认 `node scripts/verify.mjs` 通过。下一阶段开始时，这份报告本身也按本节提炼后删除，记录留在 Git 历史里。

### 8.6 预防堆积

- 测试、审计、打包和基准的运行输出默认写到 Git 忽略的 `dist/evidence-runs/<跑次>/`；只把审查需要引用的最终结果复制进 `docs/evidence/gate/`。
- 入库证据优先结构化 JSON/Markdown，截图只留关键状态，总量目标不超过 5 MiB，超出时在报告里写明理由。样本 PDF/EPUB/视频不复制进证据目录：合成样本放测试夹具目录，或由生成脚本重建。
- 一个阶段只维护一份计划和一份报告，路径固定，不带阶段名；返工和复核在原报告内追加。
- 登记表为阶段性文档标注 `retireAfter: <阶段>`；当前阶段晚于该值时文档检查失败，提醒执行整理。阶段顺序按编号比较，不写死阶段列表；反例见 `scripts/check-docs.test.mjs`。
